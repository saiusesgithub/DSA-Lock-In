class Solution {
    public List<List<Integer>> findDifference(int[] nums1, int[] nums2) {
        List<Integer> list1 = new ArrayList<>();
        List<Integer> list2 = new ArrayList<>();

        for (int i = 0; i < nums1.length; i++) {
            boolean found = false;
            for (int j = 0; j < nums2.length; j++) {
                if (nums1[i] == nums2[j]) {
                    found = true;
                    break;
                }
            }
            if (!found && !list1.contains(nums1[i])) {
                list1.add(nums1[i]);
                found = false;
            }
        }

        for (int k = 0; k < nums2.length; k++) {
            boolean found2 = false;
            for (int l = 0; l < nums1.length; l++) {
                if (nums2[k] == nums1[l]) {
                    found2 = true;
                    break;
                }
            }
            if (!found2 && !list2.contains(nums2[k])) {
                list2.add(nums2[k]);
                found2 = false;
            }
        }
        List<List<Integer>> result = new ArrayList<>();
        result.add(list1);

    }
}

HashSet approach is clearly the one I'd keep. The 18ms number doesn't make it a worse algorithm.

For arrays of lengths n and m, you're doing roughly:
Build set1 → O(n)
Build set2 → O(m)
Scan nums1 → O(n)
Scan nums2 → O(m)

HashSet add() is average O(1), so:

TC: O(n + m) average
SC: O(n + m)

Your brute-force version is much worse. You have the nested searches plus list.contains(), which itself is linear. 
Worst case is roughly O(nm + n² + m²), with O(n + m) output/storage.

One thing I particularly like in your HashSet solution is this:

if (set2.add(nums1[k])) {
    list1.add(nums1[k]);
}

You're exploiting the return value of HashSet.add():

already exists → false
newly inserted → true

So it simultaneously tells you "this wasn't in nums2" and prevents duplicates from being added to list1. Nice.
