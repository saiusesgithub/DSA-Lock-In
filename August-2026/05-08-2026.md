```java
class Solution {
    public double findMaxAverage(int[] nums, int k) {
        int begin = 0;
        int end = 0;
        double sum = 0;
        double maxAverage = 0;
        while (end - begin != k) {
            sum += nums[end];
            end++;
        }
        end--;
        while (end < nums.length) {
            double avg = (double) (sum / k);  
            if (avg > maxAverage || maxAverage == 0) {
                maxAverage = avg;
            }
            sum -= nums[begin];
            begin++;
            end++;
            if (end == nums.length) {
                break;
            }
            sum += nums[end];
        }
        return maxAverage;
    }
}
```

A few important observations:

Your maxAverage == 0 fix works, but it is fragile

You originally initialized:

double maxAverage = 0;

That fails when every possible average is negative.

Using:

if (avg > maxAverage || maxAverage == 0)

patches some cases, but 0 is also a legitimate average. A cleaner approach is to initialize the maximum using the first complete window instead of using 0 as a sentinel.


You do not actually need begin and end

For a fixed window of size k, one loop index is enough after calculating the first window.

Conceptually:

Calculate sum of indices 0 to k - 1.
Store it as maxSum.

For every next index i:
    Add nums[i].
    Remove nums[i - k].
    Update maxSum.

A simpler version would be:
```
class Solution {
    public double findMaxAverage(int[] nums, int k) {
        double windowSum = 0;

        for (int i = 0; i < k; i++) {
            windowSum += nums[i];
        }

        double maxSum = windowSum;

        for (int i = k; i < nums.length; i++) {
            windowSum += nums[i];
            windowSum -= nums[i - k];
            maxSum = Math.max(maxSum, windowSum);
        }

        return maxSum / k;
    }
}
```
This is not asymptotically faster than yours. Both are O(n). It is just easier to reason about because:

no manual end--
no boundary break
no special handling for negative averages
no repeated division for every window

Also, don’t worry about the 4ms runtime. Your algorithm is already optimal. The meaningful improvement here is code clarity, not chasing LeetCode timing variation.

Most importantly, you reached sliding window by analyzing what the brute-force version repeatedly recalculated. That is exactly how this pattern should click.
